# AC7 普通屏幕原生 DLSS：需求基线与接入验收

## 1. 目标与范围

硬件目标为 RTX 5080、5120×1440 普通屏幕。功能目标为：

```text
游戏原生低分辨率场景及真实渲染数据
  → 超宽屏周边压缩 NR，位于 SR 之前
  → DLSS SR 重建到显示分辨率
  → 合适位置的场景后处理、色调映射
  → 使用无 HUD 场景及独立 UI 信息的 FG/呈现
  → 屏幕输出
```

这是一张语义流程图。UI 合成、FG 以及部分后处理的精确顺序，需要按实际 SDK 路径和 AC7 渲染顺序确认；不能靠效果名称推断。

本需求优先级：

1. 正确的数据来源、坐标约定、颜色空间、时序和资源生命周期。
2. 干净的场景输入及 UI 分离。
3. Pre-SR NR、SR、FG 的正确串联。
4. 超宽屏 NR 的中心保护与周边减负。
5. 在以上条件成立后测量性能和调节质量。

优先复用现成组合；没有经确认达标的 AC7 组合时，再做最小的游戏专用适配。本文件只针对普通屏幕。

## 2. 不满足目标的路径

Magpie 的窗口捕获方案可保留为性能和观感对照，但不作为目标实现。其捕获图像已经包含游戏抗锯齿、后处理及 UI，光流估算也不能替代引擎原生运动矢量。

此前准备的 [Magpie 效果组](Presets/AC7-Magpie-PreSR-NR-SR-FG.json) 只实现外部处理顺序。其离线配置检查通过不代表符合本需求，也不是原生接入的替代品。

以下现象都不足以判定原生接入正确：

- 插件菜单显示 NR/SR/FG 已打开。
- NGX 创建或求值返回成功。
- 提交了尺寸正确但语义未确认的纹理。
- 提交全零深度/速度、把未知 jitter 设为零，或用未经确认的相机参数继续运行。
- 截取最终画面后移除或遮盖 HUD。
- 对带原 TAA、锐化和色调映射的结果再次执行 SR。

## 3. 原生输入数据契约

“所有原生需要的数据”指所选 NR/SR/FG SDK 和启用功能实际要求的数据，不是机械地填满所有可选指针。对 SDK 明确支持的自动曝光等模式可以评估，但必须确认颜色语义和实际行为，不能把它当作未知输入的掩盖。

| 数据 | 必须确认的内容 | 验证方式 |
| --- | --- | --- |
| 场景颜色 | 在适合替换原时序处理的阶段取得；无 HUD、无最终显示色调映射/锐化；明确格式、线性空间和预曝光 | 导出纹理及其 shader 资源绑定，对照前后阶段 |
| 原生深度 | 来源、正向/反向 Z、设备深度或线性深度、采样尺寸与有效区域 | 深度可视化；近远物体、天空、相机移动对照 |
| 原生运动矢量 | 相机及移动物体运动、编码、方向、单位、是否包含 jitter、无效值处理 | 静止相机/移动物体、移动相机/静止物体、转向测试 |
| jitter | 当帧真实投影抖动，转换到 SDK 要求的输入像素空间；记录序列和分辨率依赖 | 常量缓冲/引擎数据对照及相邻帧检查 |
| 曝光 | 颜色的 pre-exposure、实际曝光比例及曝光资源含义；确认模型颜色转换 | 暗处/亮处切换、曝光变化和数值范围检查 |
| 输入/输出尺寸 | 真实渲染尺寸、显示尺寸、纹理分配尺寸、view rect、padding、子区域原点 | 每帧描述和变化日志；不能只用纹理宽高推断 |
| 相机信息 | 所用接口需要的投影、逆投影、前后帧变换、近远平面、FOV、相机运动标志 | 与游戏视图常量匹配，验证长宽比和快速旋转 |
| 历史重置 | 相机切换、任务加载/重启、分辨率变化、暂停/恢复、设备资源替换 | 逐项触发并核对重置与画面稳定性 |
| 帧身份/时间 | 同一真实帧的颜色、深度、速度和相机数据，真实帧时间及 FG 呈现顺序 | 帧编号、队列同步和时间戳记录 |
| UI/无 HUD 颜色 | 清晰区分 UI 绘制前场景与最终图像；按 FG 后端需求取得 UI 颜色/alpha/掩码等 | HUD 开关、文本/锁定框边缘和透明 UI 对照 |
| 资源状态和寿命 | DX11/DX12 共享、读写顺序、GPU fence、格式/状态、重建及退出释放 | 正常/失败路径、切换分辨率及退出测试 |

不能把 FOV、远平面等字段的通用默认值误认为已从游戏取得。无限远投影可按其真实语义处理，不要求为了填数而制造有限 far plane。

## 4. 接入位置：替换原时序阶段，而非追加到最终图像

优先调查 AC7 原 TAA/时序处理附近的场景输入。Luma 的通用 Unreal 模块可作为识别和接入候选，但仍须通过实际采样验证。

“干净画面”应定义为适合所选 SDK 的场景数据，不是删掉游戏的一切渲染步骤。透明、雾、云、景深等可能跨越多个阶段，需要确认 AC7 的实际顺序和 SDK 的适用位置；场景本身的正确合成不能为追求字面上的“无后处理”而破坏。

要求是明确记录并排除不该进入 NR/SR 的最终显示处理和 UI，确认 SR 替换原 TAA/放大阶段，避免双重时序处理或二次空间放大。

SR 输出后还必须处理游戏后续纹理尺寸和采样常量。Luma 当前按原 TAA 输出尺寸写回的路径不能仅靠改宽高升级为低输入/高输出 SR。

## 5. Pre-SR NR 的超宽屏适配

### 5.1 采用的思路

需求采用 FoveatedDLSS5 类型的“中心保持质量、周边降低 NR 工作密度”，但不要求直接使用其发布二进制。

FoveatedDLSS5 原版文档明确仅支持 Post-SR NR，其实现不能原样放到 Pre-SR。wilsjo2 的周边空间压缩实现已描述 Pre-SR 路径及颜色/深度/运动数据的一致变换，更适合作为源码参考。

### 5.2 期望管线

```text
正常渲染坐标中的干净场景 + 深度 + 运动矢量
  → 按固定中心/周边密度进行一致的空间打包
  → NR 在压缩工作网格求值
  → 将 NR 结果/编辑量还原至正常渲染坐标
  → SR 使用正常坐标下的增强颜色及原生渲染引导数据
```

首版目标为固定中心，不增加眼动设备依赖。

### 5.3 数据正确性要求

- 中心区域按显示空间描述，再映射到实际低分辨率 view rect；独立处理宽高、padding 和对齐。
- 5120×1440 的横向视野更宽，允许主要压缩左右两侧，保持全高；不强制两个方向相同百分比。
- NR 颜色、深度和运动引导必须在同一压缩几何中。
- 运动矢量必须变换其起点与终点，不能只乘一个全局比例。
- 颜色重采样需避免周边混叠；深度不做会混合前后景的普通颜色式插值。
- 还原后交给 SR 的图像回到正常几何，不能让游戏或 SR 继续按压缩坐标采样。
- 中心、过渡、工作尺寸和曝光/分辨率变化须按需要重置 NR 历史；不把旧坐标历史用于新布局。
- 失败时保留未增强的正确场景，禁用该 NR 路径并明确报告。不得静默声称整条目标链仍有效。

### 5.4 首轮参数策略

先验证整幅 Pre-SR NR 的数据与画质，再开启周边压缩。中心保护区使用实际目标和 HUD 观察需求确定，不把其他游戏默认比例直接当作最优值。

首轮采用单次 NR、中心不额外超采样、温和的横向周边压缩和连续过渡。只有基础链正确后再调大压缩或增加 NR 处理次数。

性能比较必须包含：NR 关闭、整幅 Pre-SR NR、周边压缩 Pre-SR NR，并保持 SR/FG 和游戏条件一致。减少 NR 像素量不等于减少同等比例的游戏帧时间。

## 6. FG 独立验收

Pre-SR NR 与 SR 正确后，再接 FG，不将三项首次启动放在一次不可定位的试验里。

FG 除场景颜色外，还需要按实际后端要求取得深度、速度、相机/时间信息及无 HUD 场景/UI 信息。SR 使用的数据不能未经尺寸和单位核对就原样传给 FG。

第一目标为 2×；优先维持稳定真实输入和正确呈现节奏，再评估更高倍率。HUD 与文字不能作为场景运动的一部分被任意扭曲。

本轮已查看的 NVIDIA NGX 头文件中，SR 有 DX11/DX12 资源接口，FG 相关实现使用 DX12。实际选择 FG 路径时，先确认 AC7 的真实运行 API；若需 DX11→DX12 共享，应测量纹理传输、队列等待和呈现开销，不能假定桥接免费。

若游戏可用的其他原生 API 尚未验证，不将添加启动参数视为 API 切换成功；应以运行模块、设备/队列和实际帧捕获为证据。

## 7. 现成代码的取舍

| 组件 | 复用方向 | 不能直接假设的部分 |
| --- | --- | --- |
| Luma Unreal 通用模块 | DX11 图形 hook、TAA 候选识别、视图常量处理、运动解码、NGX SR 基础 | 已对 AC7 正确；已提供真正超分；通用相机和曝光处理已满足全部要求 |
| wilsjo2 OptiScaler NR | Pre-SR NR、颜色代理/曝光、周边压缩、空间变换和历史策略 | 原版 AC7 已有可挂接的 DLSS/FSR/XeSS 输入 |
| FoveatedDLSS5 | 中心区/边缘密度/过渡映射及可视化思路 | 其 Post-SR 发布插件可直接完成 Pre-SR |
| Cheeky | 原生 DLSS 数据截获、分区重建、Pre-SR 和传输实现参考 | 它能单独为 AC7 原版提供完整渲染输入 |
| NVIDIA NGX / Streamline 相关接口 | SR/NR/FG 实际输入契约和能力检查 | 所有功能都可在当前 API 无成本串联；NVIDIA 模型本身为可重编译开源代码 |
| Magpie Fork | 外部对照、参数与调度实现参考 | 捕获图像符合本次原生输入要求 |

现阶段没有确认到一个可直接安装、同时满足全部 AC7 条件的现成组合。**实现路径尚未选定：Luma 是取数候选，不是已确定的宿主；OptiScaler 是完整处理链候选，也不能仅因 AC7 缺少原生超分而被排除。**

两者的取数机制不同：Luma 在 TAA 绘制/计算时通过 shader 分析和资源绑定识别场景颜色、深度、速度及视图常量；OptiScaler 主要截获游戏已有 DLSS/FSR/XeSS 调用，从调用参数取得这些资源及元数据。两者都可能取得 UI 前的原生场景，但都不自动保证该游戏的颜色阶段和数据语义正确。

候选路线应比较：Luma 内扩展整条链；AC7 专用取数适配器连接 OptiScaler；扩展 Magpie 的原生数据输入/结果回接；或基于其他已验证的原生接入层。把两个 DLL 同时放入游戏不等于完成桥接，需确认 API、数据契约、资源所有权和 hook 链。选择依据应为 AC7 实际采样及各方案需补齐的工作量，而不是先固定某个框架。

### 7.1 本轮选型计划

原则：优先复用现有 NR、周边压缩、SR、FG 和呈现实现，只开发 AC7 必需的资源识别、参数转换及输出回接。外部界面与 GPU 处理是否分进程分别决策；不因需要独立控制窗口，就强制每帧跨进程处理，也不预设重写一个更小的程序。

本轮先开展源码/API 调查，不安装注入器、不改游戏文件、不启动模型求值。按下列证据评估后，再选择最小可验证原型：

| 调查项 | 必须回答的问题 |
| --- | --- |
| 游戏接入 | AC7 的候选 TAA、颜色、深度、速度、视图常量及输出回接有哪些已有代码或证据？ |
| 后端入口 | 能否通过现有 API 提交完整输入，还是需要拆出内部实现？输入/输出的所有权和设备要求是什么？ |
| Pre-SR 周边 NR | 能否在正常引擎坐标与压缩网格间正确往返，是否已有可复用实现？ |
| SR 回接 | 低分辨率输入、高分辨率输出怎样进入游戏后续处理，谁负责跳过原 TAA/空间放大？ |
| FG/呈现 | 现成路径接受哪些颜色/UI/相机资源，依赖哪个图形 API，谁持有交换链与节奏？ |
| 进程边界 | 同进程和外部程序各需要哪些新增接口、纹理共享、等待及失败回退？ |
| 维护成本 | 需改哪些模块、哪些属于通用桥接、哪些只属于 AC7？不能只按总代码量或功能列表选择。 |
| 证据等级 | 区分源码存在、离线构建/契约检查、GPU 求值、AC7 实测；缺失实机证据时只给条件性选型。 |

候选架构暂保留四类：A）AC7 适配＋OptiScaler 原有输入协议；B）Luma 内复用 NR/FG 组件；C）AC7 适配＋扩展的 Magpie 外部宿主；D）其他现有原生接入/后端。比较结果记录在 [架构选型调查](AC7-Native-DLSS-Architecture-Selection.md)。

决策门槛：先确定一条已有明确输入契约且能回接游戏的路径；若 FG 仍需独立呈现改造，明确列为未解决项，不能把 NR/SR 已复用称为完整链已落地。必要的 AC7 GPU 采样用于验证最终候选，不先依据通用模块成功编译锁定宿主。

当前保留 **AC7 专用适配器＋OptiScaler、Luma 内扩展、Magpie 扩展** 等候选，尚不排序。此前将 OptiScaler 称为首选原型的判断已撤回：AC7 实际运行 API、交换链和原生资源入口尚未确认，不能仅凭后端源码功能较全作出选型。下一阶段先完成这些运行前置调查，再评估适配工作量和接口验证顺序。详细源码证据、已通过的周边映射 CPU 测试及缺失事项见 [架构选型调查](AC7-Native-DLSS-Architecture-Selection.md)。

## 8. 当前源码检查发现的缺口

Luma 的 `Source/Games/Unreal Engine/main.cpp` 中可见：

- `sr_render_resolution_scale = 1.0f; // DLAA only`。
- 输出尺寸取自原 TAA 输出纹理，成功后写回原纹理。
- 通用路径默认启用 SR 自动曝光；SDK 允许的模式仍需与 AC7 颜色语义核对。
- 相机数据由通用视图常量识别与计算取得，其中远平面位置仍有通用处理/注释，不能当作 AC7 已验证的真实参数。
- TAA 候选过滤和尺寸判断需要在低渲染比例、超宽屏 view rect 下验证。

之前生成的 Luma 实验包只增加首次成功求值日志，不足以证明颜色、速度、曝光或相机语义正确。

## 9. 分阶段实施与验收

### 阶段 A：取得并验证原生数据

第一项必须产物为 AC7 实际飞行的 GPU/渲染采样与输入清单：

- 记录可识别的可执行文件版本/哈希、运行 API、任务和显示/渲染设置。
- 标记 TAA、色调映射、空间放大和 UI 绘制的位置。
- 导出候选场景颜色、深度、运动矢量及相应 shader、常量和有效区域。
- 至少取得静止、相机旋转、移动物体和相机切换的样本。
- 每项数据标记“已确认/未知/不适用”，保留证据来源。

未知的数据不填默认值宣称通过；错误或无法证明的数据不能进入后续性能结论。

### 阶段 B：正确 SR

- 验证原生分辨率 DLAA 接入的数据语义。
- 再接低分辨率输入、高分辨率输出，替换原 TAA/放大路径。
- 检查 HUD 仍为显示分辨率，且未被 NR/SR 处理。
- 检查快速运动、细线、飞机、导弹尾迹、云层和遮挡。

### 阶段 C：正确 Pre-SR NR

- 先整幅单次 NR，正确处理颜色空间和曝光，保留与 SR 的坐标约定。
- 使用开/关对比及运行状态证明 NR 确实求值。
- 验证模型开关、历史重置、暂停/恢复和任务重启。

### 阶段 D：超宽屏周边 NR

- 加入中心保护和连续过渡，先仅横向压缩。
- 验证颜色/深度/运动一致性和解包几何。
- 比较整幅 NR 与周边 NR 的 GPU 成本及运动画质。

### 阶段 E：FG 与呈现

- 验证无 HUD 场景、UI 数据、相机/时序和真实帧关联。
- 先 2×，测真实帧率、显示帧率、帧间隔、延迟和传输等待。
- 最后验证完整链及异常恢复。

当前尚未完成阶段 A。不能以既有离线构建、头文件检查或功能标志代替飞行采样。

## 10. 当前交付与限制

本次交付是原生接入的需求基线、数据契约、路线选择及采样验收单。没有在未知渲染数据上拼接 NR/SR/FG，也没有生成宣称已满足目标的新补丁。

此前的 Magpie 配置和 Luma 编译产物保留为对照/诊断材料。游戏目录、现有 Magpie 配置与系统设置未因本次需求调整而修改。

下一依赖是 AC7 原生渲染采样。获得样本后，才能按已证明的资源和调用位置实现游戏专用接入，并选择是否复用 DX11 路线或其他经验证的 API 路线。
